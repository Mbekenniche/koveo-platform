# ADR 1: Strict multi-repository layout

* **Status:** Accepted
* **Date:** 2026-08-04
* **Deciders:** Mohamed BEKENNICHE

---

## Context and problem statement

The project is made of five distinct subsystems, each with its own lifecycle:

1. **Platform** — infrastructure, orchestration and deployment.
2. **Applications** — the Koveo Fret information system and the parcel-tracking microservices.
3. **AI** — retrieval, agents, evaluation and inference serving.
4. **ML foundations** — algorithm implementations written without frameworks.
5. **Journal** — working notes, step records, cross-cutting decisions.

The question was how to lay these out in Git: consolidate all or part of them into a single repository, or give each its own.

---

## Decision drivers

* **No code coupling.** No shared libraries or common types between subsystems; they communicate through APIs.
* **Independent lifecycles.** The subsystems are not released, versioned or deployed together.
* **Separation of learning material from portfolio material.** The journal records what was not known at the time. It is a working tool, not something a reader should be handed alongside the code.
* **Operational simplicity.** Avoids the path-based change detection that a monorepo requires to know what to rebuild.

---

## Considered options

1. **Global monorepo** — everything in one repository, separated by directory.
2. **Partial monorepo for the platform** — `koveo-platform` holds infrastructure, Kubernetes manifests, delivery pipelines, workstation tooling and all documentation; applications and AI live separately.
3. **Strict multi-repository** — one repository per subsystem, with cross-cutting documentation and workstation tooling kept out of the platform repository.

---

## Decision outcome

**Option 3 — strict multi-repository.**

| Repository | Scope | Visibility |
|---|---|---|
| `koveo-platform` | Infrastructure and orchestration only | public |
| `koveo-apps` | Information system and parcel-tracking microservices | public |
| `koveo-ai` | Retrieval, agents, evaluation, inference serving | public |
| `ml-from-scratch` | Framework-free algorithm implementations | public |
| `koveo-journal` | Cross-cutting documentation, workstation bootstrap, step journal, calibration work | private |

**What moves out of `koveo-platform`:** the workstation bootstrap manifest and its rebuild procedure, and cross-cutting documentation — including this record.

**What stays with the system it governs:** each repository keeps its own `README.md`, and decision records scoped to a single subsystem stay in that subsystem's `docs/adr/`. A decision about how Kubernetes services are exposed belongs to the platform; only decisions spanning several repositories, such as this one, are cross-cutting.

---

## Consequences

### Positive

* **Focused history.** Each repository's log covers one domain, which makes it readable and makes `git log` a useful navigation tool rather than noise.
* **Per-repository access control.** Visibility and permissions are set independently — which is what allows the journal to stay private while everything else is public.
* **Independent delivery.** No cross-repository release constraint between platform, applications and AI.
* **The platform repository stays readable.** A reader opening `koveo-platform` finds infrastructure, not a mixture of infrastructure, personal notes and machine setup.

### Negative / accepted risks

* **Repository sprawl.** Five repositories to configure and keep consistent: hooks, licences, ignore rules, and later, delivery pipelines duplicated rather than shared.
* **Cross-repository changes cost more.** A change spanning two subsystems — an API contract change in `koveo-ai` consumed by `koveo-apps` — needs two commits in two repositories, with no atomic revert across both.
* **Cross-cutting records are not publicly visible.** Because `koveo-journal` is private, this record and every future cross-cutting decision cannot be read by anyone evaluating the public repositories. This is a deliberate trade of portfolio visibility against keeping learning material out of sight; it is the most expensive consequence of this decision and should be revisited if the balance changes.
* **The bootstrap manifest is separated from the platform it builds.** Someone cloning `koveo-platform` does not get the toolchain needed to work on it.
